# Photon Neutron sandbox captures

Every file here is a response really returned by `prescriptionScreen` on
`https://clinical-api.neutron.health/graphql` for the synthetic demo patient,
with the timestamp of the capture. No credentials and no tokens are stored
here. This directory is the only place in the repo that holds captured sandbox
responses.

## One source of truth

| Path | What it is | Who reads it |
|---|---|---|
| `*-screen.json` | One normalized capture per demo draft, written by the live check script with its `recordedAt` | the generator below |
| `../../src/lib/clinician/photonRecorded.ts` | Generated from the files above. The single set the UI falls back to | the panel, through `photonFallback` |
| `raw/*-raw.json` | The raw GraphQL envelopes of the first live run, kept as evidence | nothing, by design |

The UI reads exactly one set: the generated module. Nothing reads `raw/`, and
nothing reads these JSON files at runtime. That is what keeps the
"Recorded sandbox response" label honest, because the only way a capture can
reach that label is through the generated module, and the only way into the
generated module is a real sandbox response the script received.

| File | Draft | What the sandbox returned |
|---|---|---|
| `ciprofloxacin-500-mg-screen.json` | Ciprofloxacin 500 mg | DRUG, MODERATE, warfarin anticoagulant effect |
| `amoxicillin-500-mg-screen.json` | Amoxicillin 500 mg | ALLERGEN, MODERATE, penicillin G, plus a DRUG alert with warfarin |
| `ibuprofen-200-mg-screen.json` | Ibuprofen 200 mg capsule | DRUG with aspirin (MAJOR), warfarin and metoprolol, plus ALLERGEN for the ibuprofen allergy |

`raw/` holds the same three drafts as the clinical API returned them, envelope
and all, from the first live run on 2026-10-03. They are evidence of what the
sandbox said, not an input to the build, and they are not regenerated by the
script. If the catalog ever changes drug ids, re-capture them or drop them
rather than leaving them to contradict the generated module.

## Which ibuprofen product the demo screens

The sandbox carries two 200 mg ibuprofen products. The demo screens exactly
one of them:

- screened: `med_01KZEG3HFJQF4VK0AXCYAVS77J`, "Ibuprofen Oral Capsule 200 MG".
  This is the id in `src/lib/clinician/photonTreatments.json`, in every capture
  here, and in the passing live checks. The panel labels it
  "Ibuprofen 200 mg capsule" so the product is unambiguous on stage.
- not screened: `med_01KZEG3HFG5M9FYXPGJHS67FMR`, "Ibuprofen Oral Tablet 200 MG".
  It is deliberately absent from the catalog, and a test fails if it reappears
  there.

Both return the same four alerts for this patient, but only one id may be in
the tree, so the capsule is it.

## Re-capturing

Re-capture after changing the catalog or the demo patient:

    npx tsx --env-file=.env.local scripts/photon-live-check.mts

The script also runs sync-patient twice to prove it stays idempotent. It
rewrites `*-screen.json` and the generated module, and leaves `raw/` alone.

Screening itself never writes to the Photon org: it resolves the patient with
a read-only lookup. Creating him is the separate `api/photon/sync-patient`
function's job, and the script calls it first.

## Note on credentials

`prescriptionScreen` resolves a user, and the machine to machine client has
none, so the live screen needs a user access token in `PHOTON_USER_TOKEN`
(server side only). Without it the call fails with
`Could not get user for request` and the panel falls back to these captures.
Patient sync, treatment lookups and allergen lookups work with the machine to
machine credentials alone.

User access tokens expire. `PHOTON_USER_TOKEN` must be added to the Vercel
environment variables at ship time and refreshed when it lapses. An expired
token is not an error page: the panel falls back to these captures under the
"Recorded sandbox response" label and shows the reason.
